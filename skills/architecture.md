# ESDLC App Constitution

This is the **standing ruleset** for every app the factory builds. `spec` plans to it, `build` codes to it, `test-author` tests to it. It is derived from proven production iOS conventions, **modernized for greenfield** on the current iOS baseline (see § Delta from a prior baseline).

It does **not** restate how to write modern Swift — that is delegated to vetted, vendored skills (§ Vendored skills). This file owns only the project-specific rules those skills cannot know: the pattern we fix, the archetype catalog, the scope ceiling, shared-file ownership, the capability allow-list, and precedence.

## Precedence (read first)
When this constitution and a vendored skill disagree, **this constitution wins.** The clearest case: we fix **MVVM** (§ Pattern); any skill that pushes Model-View or "refactor the view-model away" is overridden on that point and its other advice still applies. Vendored skills are *trusted-authored guidance*, never authority over this file, and never over untrusted client input.

## Stack
- **Current iOS baseline** (iOS 26 — one version back from latest for device availability; matches what the `-pro` skills assume), **Swift 6**, **SwiftUI**. **Dependencies via SPM only** (no CocoaPods); the Xcode project is **generated by XcodeGen** (`project.yml`) — regenerated, never hand-merged — which is how we avoid `pbxproj` conflicts (see `scaffold`).
- **Observation framework** (`@Observable`) for view models.
- **async/await** only — no completion handlers.
- **swift-testing** (`@Test` / `#expect`) — not XCTest.
- Persistence: **SwiftData** for list/CRUD archetypes; `UserDefaults`+`Codable` for trivial state. No external network.

## Pattern — MVVM (modern, fixed)
> Fixed choice (confirmed by Vlad). This **overrides** any vendored skill that favors Model-View (see § Precedence). Logic that must be unit-tested lives in pure types (`BalanceCalculator`, `ExpressionEvaluator`, `ItemStore`) **and** is exposed through the `@Observable` view model.

```swift
@Observable
final class ShoppingListModel {
    private(set) var items: [Item] = []
    private let store: ItemStore
    init(store: ItemStore) { self.store = store }   // DI via init
}

struct ShoppingListView: View {
    @State private var model: ShoppingListModel      // owns lifecycle (replaces @StateObject)
    var body: some View { ... }
}
```
- **DI everywhere** — constructor injection + `@Environment`. **No singletons.**
- **Repository pattern** — protocol-first data access (`protocol ItemStore { ... }`), so tests inject fakes.
- **Isolation is explicit, never drifted.** `@MainActor` on view models and UI-touching types; **pure/data types are `nonisolated`** (and `Sendable` where they cross actors). Fix strict-concurrency diagnostics with `nonisolated`/`Sendable`, **never `@unchecked`**.
- **Child two-way bindings** take `@Bindable var model` (gives `$model.field` in the child); the owning view holds the VM via `@State`. Never `@StateObject` (that's legacy `ObservableObject`).
- **Async `load()` discipline** — `guard !isLoading` re-entrancy guard (set/reset via `defer`); structured concurrency (no detached `Task {}` inside `load()`, so cancellation propagates); catch `CancellationError` **silently** (normal when navigating away); gate auto-load so re-appearance doesn't refire: `.task { if vm.items.isEmpty { await vm.load() } }`.
- **No god objects.** A `…Manager` that fetches + caches + formats + navigates is a smell — split along responsibilities (one reason to change per type).
- **Custom error enums** conforming to `LocalizedError`. **No force-unwraps.** All errors handled.
- Lists render via `List` / `LazyVStack` (virtualized), never `ScrollView`+`VStack` for data.

## Project layout (feature-first, buildable folders)
Organize **by feature, not by type**. Canonical shape:
```
App/               ← @main entry, composition root (router/TabView)              ← SCAFFOLD-OWNED
Features/<Name>/    ← one vertical slice per feature                             ← FEATURE-AGENT-OWNED
  ├── Views/         SwiftUI views (+ #Preview, accessibility)
  ├── ViewModels/    @Observable @MainActor view models
  └── Models/        feature-private types only
Core/ (≈ Shared/)  ← cross-feature infra: shared Models, Storage, Networking, Extensions ← SCAFFOLD-OWNED
UI/                ← design system: Components (PrimaryButton, ErrorView), Theme/DesignTokens ← SCAFFOLD-OWNED
Tests/             ← swift-testing suites (AC-ID tagged)
project.yml (XcodeGen), Info.plist, Assets.xcassets                             ← SCAFFOLD-OWNED
```
**Tiny apps use a flattened subset** — the three demo archetypes collapse `Core/`+`UI/` into one `Shared/` and inline a feature's `Views/ViewModels/` (see `examples/`). Rule: **materialize only the directories that receive real files this run**; document the full intended layout in the app's `ARCHITECTURE.md`. The `.xcodeproj` is generated from `project.yml` (never hand-edited); adding a file to a source folder needs no project edit.

## Shared-file ownership (critical for parallel build)
To stop last-writer-wins from silently dropping screens:
- **The scaffold task owns** `App/`, `Shared/`, `project.yml`, `Info.plist`, `Assets.xcassets`, the composition root (router/tab), and shared models.
- **The `design` stage owns** `Sources/DesignSystem.swift` — the single source of visual truth (palette + type + spacing + radii + the `DS*` components), **derived from the app's own brief** (Apple HIG defaults when the brief gives no direction; never a house brand). Runs after scaffold, before build. The agent returns validated **tokens**, the spine renders the Swift — so the look varies per app but the code is fixed and always compiles. Feature agents **consume** it (`DS.*`) and never edit it.
- **Feature agents may only add files inside `Features/<Name>/`** and **declare needs** (routes, model fields, Info.plist keys, deps) as structured data. The scaffold/merge step applies declarations deterministically, hard-failing on conflict. **Every feature screen styles through `DesignSystem.swift`** — no hardcoded colors/fonts (enforced by `audit`).

## Capability allow-list
Allowed: local persistence, on-device computation, standard SwiftUI UI, system share sheet, local notifications.
**Disallowed** (intake must refuse): external network / `WKWebView` to remote URLs, camera/mic/contacts/location, accounts/auth, payments, background modes, arbitrary file access. A static scan enforces this as a required check.

## Supported archetypes
The factory only builds these. Each ships defaults so `intake` can proceed without questions and `spec` can map straight to a screen set.

### `shopping-list`
- **Screens (2):** `ItemList` (add / check / delete, swipe-to-delete), `AddItem` (text field + save).
- **Model:** `Item { id, title, isDone, createdAt }`; store = SwiftData.
- **Default ACs seed:** add non-empty item persists across relaunch; checking toggles done + reorders; delete removes.

### `bill-splitter` (Splitwise-style)
- **Screens (3):** `People` (add participants), `Expenses` (add expense: payer + amount + split mode), `Balances` (per-person owed/owing).
- **Model:** `Person { id, name }`, `Expense { id, payerID, amount, splitMode }`; store = SwiftData. Math in a pure, unit-tested `BalanceCalculator`.
- **Default ACs seed:** even split sums to total (±1 cent); per-person balance nets to zero; deleting an expense recomputes.
- **Clarify-if-missing:** split evenly vs by share (default: evenly).

### `calculator`
- **Screens (1):** `Calculator` (keypad + display).
- **Model:** pure `ExpressionEvaluator` (no persistence); optional last-result in `UserDefaults`.
- **Default ACs seed:** correct arithmetic for +−×÷ with precedence; divide-by-zero shows an error state, never crashes; chained operations.

### `generic-list` (fallback)
- **Screens (≤3):** one list + one add/edit; same shape as `shopping-list` with a configurable item schema.

All four are **local-only** and sit entirely inside the capability allow-list — no clarification can push them out of it.

## Info.plist baseline
- `ITSAppUsesNonExemptEncryption = false` (skips export-compliance gate).
- Usage-description strings only for allow-listed capabilities actually used.

## Naming
`camelCase` properties (`itemCount: Int`), `PascalCase` types (`ShoppingListModel`), verb functions (`addItem()`), one primary type per file.

## Verified gotchas (golden path — proven in `examples/shopping-list`, 2026-10-28)
Both were caught by actually compiling/running the reference app, not by review. The generating skills must honor them:
- **SwiftData + `SortDescriptor` on `Bool` does not compile.** `Bool` isn't `Comparable`, and `SortDescriptor`'s `Bool` overload requires `NSObject` (a `@Model` isn't one). So a `FetchDescriptor` **cannot** sort by a `Bool` keypath (e.g. `\.isDone`). Sort by a `Comparable` stored property (`Date`, `Int`, `String`) in the fetch, then partition on `Bool` in Swift. → `build`, `scaffold` (swiftdata-pro).
- **Test `ModelContainer` must be retained for the test's lifetime.** A factory that returns a store/VM wrapping `container.mainContext` while `container` is a function local → the container deallocates on return and the next `save()` SIGTRAPs (signal 5). Hold the `ModelContainer` as a **stored property** of the `@Test` struct (swift-testing news a fresh instance per test → isolation *and* retention). App code is unaffected (container owned by `.modelContainer(for:)` at the App scene). → `test-author` (swiftdata-testing).

Two more from the architecture kit (`llm-architecture-layer`), to stay robust across toolchains:
- **`@MainActor` VM init from a non-isolated `View.init` can fail** — *"call to main actor-isolated initializer in a synchronous nonisolated context"* — on setups where SwiftUI's `View` isn't main-actor-isolated and `SWIFT_DEFAULT_ACTOR_ISOLATION` isn't `MainActor`. On our iOS 26 / Swift 6.2 baseline it compiles (the examples prove it), but don't lean on the toolchain: **annotate isolation explicitly** (our default), or set `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` project-wide and mark pure/data types `nonisolated`. → build, scaffold.
- **No placeholder files inside an Xcode synchronized-group source root.** With `PBXFileSystemSynchronizedRootGroup`, every file under the root auto-joins the target — a stray `.gitkeep` becomes a bundle resource and duplicates collide into *"Multiple commands produce…"*. XcodeGen uses explicit file refs (largely immune), but `scaffold` must still materialize only directories that receive real files and document the rest in `ARCHITECTURE.md`. Never move `Preview Content/` (its path is pinned in `DEVELOPMENT_ASSET_PATHS`). → scaffold.

## Delta from a prior production baseline (deliberate modernization)
| Prior baseline (iOS 14+, Combine-era) | ESDLC (greenfield, current baseline) |
|---|---|
| `ObservableObject` + `@Published` | `@Observable` macro |
| `@StateObject` | `@State` (owns the `@Observable`) |
| XCTest + hand mocks | swift-testing + protocol mocks |
| CocoaPods + `.xcworkspace` | SPM-only |
| `[weak self]` in Combine closures | structured concurrency; handle `Task` cancellation |
Unchanged from the prior baseline: MVVM, DI via init + Environment, Repository pattern, async/await, custom error enums, no force-unwraps, @MainActor for UI.
